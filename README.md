### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удаленно включать/отключать отопление в своих домах
- Система позволяет изменять статус датчика - активен\неактивен
- Система поддерживает добавление новых датчиков отопления с участием специалиста
- В системе предусмотрены API методы для создания\обновления\удаления датчиков

**Мониторинг температуры:**

- Пользователи могут получать список всех датчиков
- Система получает данные о температуре от внешнего API
- Пользователи могут получать данные о температуре в указанной локации, изменять температуру
- В системе предусмотрены API методы для создания\обновления\удаления датчиков, но добавление датчиков 
- Система поддерживает различные системы измерения температуры

### 2. Анализ архитектуры монолитного приложения

Архитектура приложения представляет собой монолит на Go с СУБД Postgres. 
Всё синхронно. Никаких асинхронных вызовов, микросервисов и реактивного взаимодействия в системе нет. 
Всё управление идёт от сервера к датчику. 
Данные о температуре также получаются через запрос от сервера к датчику.
Самостоятельно подключить свой датчик к системе пользователь не может.

Для развертывания приложения используется контейнеризация - docker и docker-compose
Информация о температуре датчика получается из внешнего REST API 

### 3. Определение доменов и границы контекстов

**Домен управления устройствами**

Поддомен управления списком устройств:
- Добавление\изменение\удаление устройств и их параметров
- Получение статуса устройств
- Получение списка устройств

Поддомен управления состоянием:
- Управление режимами работы (изменение температуры, освещенности и т.д.)

**Домен мониторинга показателями устройств**

- Получение данных датчиков
- Предоставление агрегированных сведений

### **4. Проблемы монолитного решения**

- Масштабируемость: Невозможность масштабировать отдельные компоненты независимо
- Развертывание: Требует остановки всего приложения при обновлении
- Технологическая связанность: Все компоненты используют один стек технологий
- Отказоустойчивость: Отказ одного компонента влияет на всю систему
- Разработка: Сложность координации разработки при росте команды
- Тестирование: Сложность изолированного тестирования компонентов

# Задание 5. Работа с docker и docker-compose

В каталоге temperature-api реализовано приложение на Go, обеспечивающее предоставление
данных с датчиков температуры

## API Endpoints

### 1. Получение температуры по локации
- **Метод**: `GET`
- **Путь**: `/temperature`
- **Параметры**: `location` (обязательный)
- **Пример**: `GET /temperature?location=Living Room`

### 2. Получение температуры по ID датчика
- **Метод**: `GET`
- **Путь**: `/temperature/{sensorId}`
- **Параметры**: `sensorId` (в пути)
- **Пример**: `GET /temperature/1`


Добавлен Dockerfile для сборки приложения, в docker-compose внесены необходимые для запуска приложения изменения
